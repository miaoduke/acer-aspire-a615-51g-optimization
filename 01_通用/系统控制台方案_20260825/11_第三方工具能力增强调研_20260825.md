# 第三方工具能力增强调研 — 能否借外部工具扩展 Windows 侧软硬件控制
> 机器: Acer A615-51G (i5-8250U / MX150 / Win11 Build 26200) | 控制台Win v6.5 (零依赖铁律)
> 日期: 2026-08-25 | 方法: 网络穷尽调研 (官方文档/GitHub issues/社区实测) × 本机状态现场实测交叉
> 定位问题: 除自研控制台外, MSI Afterburner / ThrottleStop / XTU / NBFC / FanControl / Process Lasso 等能否带来更多能力?

---

## 一、总结论 (先说答案)

1. **GPU 侧 (Afterburner 等): 无增益。** MX150 官方不支持笔记本; 本机 nvidia-smi 实测功耗表为垃圾值 (power.limit=[N/A], 默认/上限=5001W, VBIOS 功耗表未初始化), 任何第三方滑块工具无从下手。
2. **CPU 侧 (ThrottleStop): 存在一项重大潜在增益, 但被本机一个开关闸死。** 本机实测 **HVCI=1 / VBS=Running (内存完整性开启)** —— 这是 ThrottleStop 降压/功耗墙控制在 Windows 上失效的直接原因; 而 Linux 侧 -50mV 成功已证明本机固件不锁。关闭内存完整性是解锁的第一步 (**必要条件, 但未必充分** —— 个别机型还需 BIOS 关虚拟化, 见 B 节), 属安全权衡的用户决策项。
3. **进程侧 (Process Lasso): 其核心增值 EcoQoS 是微软原生 API**, 控制台可零依赖自实现 → 已列入代做。
4. **风扇侧 (NBFC/FanControl): 双重确认死路。** 本机 EC (ENE KB9022Q) 社区多轮探测失败, FanControl 官方明言笔记本基本不支持且无 Acer 插件。
5. **XTU: 死路。** 官方仅支持 K/X 系列, 8250U 被明确移除。

## 二、逐工具裁决表

| 工具 | 裁决 | 关键证据 |
|---|---|---|
| **MSI Afterburner** | ❌ 无增益 | 官方不支持笔记本 (guru3D/Tom's Hardware 论坛 Moderators 一致声明; Unwinder 不为移动 GPU 准备测试样本); **本机实测 nvidia-smi: power.limit=[N/A], 默认/上限=5001W 垃圾表** (VBIOS 功耗表未初始化), 滑块无从下手; 曲线降压理论可行但驱动版本敏感 (LTT 论坛: 528.24/528.49 前后行为变化), 脆弱不值当 |
| **RivaTuner OSD** | ➖ | 游戏内 OSD 早已⛔ (注入类) |
| **ThrottleStop 9.6** | 🌟 **有条件重大增益** | ①850U 教程存在 (Acer Swift 3, 异机型仅作旁证 —— FIVR 锁是每机固件配置); ②功能面 = FIVR 降压 + TPL(PL1/PL2) + Turbo Ratio Limits + BD PROCHOT 解除; ③NotebookTalk 用户实测 (TwistedAndy/i.bakar 等): VBS/内存完整性开启时负偏压不生效; ④**本机实测 HVCI=1/VBS=Running**; ⑤Linux -50mV 生效证明本机固件不锁 → 需先关内存完整性 (必要非充分, 见 B 节) |
| **Intel XTU** | ❌ | 官方: 仅 K/KF/HK/X/XE 系列; 8250U 在 unsupported platform 名单 (gimdh/Intel-XTU-Install-Helper); 旧版 msiexec 绕过对现行 7.14/10.0 已无意义 (旧版安装包已停发) |
| **NBFC / nbfc-linux** | ❌ | A615-51G ≈ A515-51G (同 BIOS/手册, issue #550 原话), EC=ENE KB9022Q D; 两轮实质探测 (#550/#984): 找到温度寄存器 (0xB0/0xB3/0xB4) 但无人找到风扇写寄存器, 持有 kb9022.pdf 数据手册者仍失败; 另有用户解锁 BIOS 后确认风扇曲线仍不可改 (#550) |
| **FanControl (Rem0o)** | ❌ | 官方 FAQ: "Mostly no"; 插件仅 Dell/Lenovo/ARC 等, 无 Acer; 维护者指路 NBFC (而 NBFC 对本机已❌) |
| **HWiNFO64** | ➖ | 监控与 LHM 重叠; 笔记本无风扇控制能力 |
| **Process Lasso** | ⚠️ 不引入, 自实现 | 其 Efficiency Mode 持久化规则 = 包装微软 **EcoQoS API** (SetProcessInformation PROCESS_POWER_THROTTLING_EXECUTION_SPEED, Win11 原生); 控制台 C# P/Invoke 即可实现同等能力, 保持零依赖 |
| **Acer Care Center** | 🔍 用户侧一次验证 | Battery Health Mode (80%阈值)/校准经 WMI GUID 79772EC5 下发 (出处: acer-wmi-battery 项目调研, 更早会话; 本会话未独立复核); 本机全枚举未暴露该 GUID → ACC 大概率也不显示 (2017 机型早于此特性); 但装一次即可终局判定, 兼得跨系统 EC 持久性验证 (Linux 代做 #4) |
| **SetTimerResolution / ISLC 类** | ➖ | 计时器分辨率属延迟调优, 非功耗/硬件控制范畴 |

## 三、本机关键事实链 (Windows 降压能力的完整逻辑)

```
Linux 侧 -50mV 写 MSR 0x150 生效
        ↓ 证明
本机固件/BIOS 未设置 FIVR lock 位, 微码未阻断
        ↓ 但
本机 Windows 实测 HVCI=1 + VBS=Running (核心隔离→内存完整性 开启)
        ↓ NotebookTalk 社区实测 (TwistedAndy/i.bakar 等, 有原话支撑)
"VBS/内存完整性开启时负偏压不生效; 需禁用 VBS"
(部分机器还需 BIOS 关虚拟化 —— 因机型而异)
        ↓ 结论
内存完整性开关是 Windows 侧降压/PL1PL2 的第一道闸门 (纯软件策略, 非硬件限制);
能否只开这一道闸即生效, 需本机逐级实测
```

**附带发现**: 微软 2025-03 起 Defender 标记 WinRing0 驱动 (CVE-2020-14979, 官方威胁百科收录), 波及 LHM/FanControl/Afterburner/HWiNFO 全家; 微软随后表示"重新评估检测逻辑" (政策存在反复, 非单向终局)。本机 LibreHardwareMonitorLib.dll 在位、历史会话温度链路正常, 但拦截记录未以管理员权限复核 → 维持监测清单。若未来 LHM 被 Defender 拦截, 控制台温度监控将退化为 ACPI 热区路径。

## 四、行动建议

### A. 控制台原生新增 (零依赖, 无争议)
| # | 项 | 说明 |
|---|---|---|
| 1 | **EcoQoS 进程效率模式** | 进程页右键菜单"效率模式(开/关)" + settings.ini 持久化规则 (按进程名); P/Invoke SetProcessInformation; 对后台常驻程序 (同步盘/更新器) 收益直接 |
| 2 | PowerThrottling\DisableUserPresenceQos 注册表开关 | 微软文档原生项, 防"前台闲置降 QoS"干扰基准测试 (可选暴露) |

### B. 用户决策项 (涉及安全权衡, 不替用户做主)
| 项 | 收益 | 代价 |
|---|---|---|
| 关闭"核心隔离→内存完整性" + 运行 ThrottleStop | FIVR 降压 (-50mV 起, 对齐 Linux 战果: 降温+省电+免降频) · PL1/PL2 直控 · Turbo Ratio 手动 | ①失去 HVCI 内核攻击面防护; ②Defender 可能标记 TS 的 WinRing0 变体; ③第三方常驻工具违背绿色单文件哲学 (作为伴生工具可接受) |

⚠️ **必要性 ≠ 充分性**: 社区经验因机型而异 —— 多数机器关内存完整性即可 (TwistedAndy: 可保留 Hyper-V/虚拟化), 但部分机器 (i.bakar 案例) 还需进 BIOS 关闭虚拟化才生效; 若走到那一步, Hyper-V/WSL2/沙盒全部受累。**建议逐级实测**: 只关内存完整性 → TS 写 -10mV 并读回验证 → 无效再考虑 BIOS 层。

### C. 用户侧一次性验证
- 安装 Acer Care Center 看是否出现"电池充电限制"选项 (预期: 无; 用于终局关闭这条线)
