## 一、终端 TUI 监控类

| 工具 | 技术栈 | 定位与亮点 | 资源占用 | 对本项目价值 |
|---|---|---|---|---|
| **btop++** | C++ | 全能一屏监控（CPU/内存/磁盘/网络/GPU/进程），256色/truecolor、braille 图、主题系统 | ~20MB，<1% CPU | ★★ GPU 面板与"一屏总览"布局参照；主题系统 YAGNI 不学 |
| **htop** | C | 进程管理标杆：树视图/多选/F键/鼠标 | ~5MB | ★ 进程页交互范式（若做精简进程视图） |
| **top** | C (procps) | 永远在场零依赖 | 忽略不计 | 参照系 |
| **Glances** | Python(psutil) | TUI+Web+REST+Prometheus 导出+C/S 模式；跨平台 | 60–120MB，2s tick 数个点CPU | ★ Web 导出思路（二期可选）；重，不直接采用 |
| **bottom (btm)** | Rust | 图表优先的实时曲线监控 | 低 | ★ 曲线呈现风格 |
| **s-tui** | Python(urwid) | **温度/频率/功耗/利用率曲线 + 限流原因标注（T/W 组合标签）+ 内置压力测试** | 低 | ★★★ 限流原因可视化范式（我们 G1 已对标 ThrottleStop 实现）；其"阈值触发脚本"机制值得借鉴 |
| **nvtop** | C | NVIDIA/AMD GPU 专用监控 | 极低 | Mission Center 的 GPU 后端即它；MX150 数据源 nvidia-smi 已覆盖 |
| **zenith / nmon / atop** | Rust/C | 各有侧重（atop 历史回放） | — | atop 的"历史落盘回放"思想已在 G3 落盘实现 |

## 四、Web 控制台类

| 工具 | 定位 | 关键特性 | 对本项目价值 |
|---|---|---|---|
| **Cockpit** | 服务器 Web 管理台 | **socket 激活：不用时零后台开销**；系统集成 API 不另起炉灶；内置终端；多机 SSH 聚合；**+PCP 可得历史指标** | ★★ 若未来需要"手机/平板查看笔记本状态"，Cockpit 模块或 textual-web 是轻路径；单机日常场景收益低 |
| **Netdata** | 实时监控服务器 | 毫秒级指标、零配置、自动仪表盘；云同步可选 | 单机过重（常驻 agent 违背省电原则），排除 |
| **Glances -w** | 轻量 Web 视图 | 一条命令出 HTTP 页 | 二期可选的最小 Web 方案 |
| **Prometheus+Grafana / Zabbix** | 舰队级监控 | 长期趋势+告警 | 明确超范围（YAGNI），G3 TSV 落盘已覆盖单机复盘 |

## 五、开发框架层（选型依据）

| 框架 | 2026 状态 | 观察 |
|---|---|---|
| **Textual** | v8.2.1（2026-03），35k+ stars，活跃 | TUI+`textual serve` 浏览器双输出；若做 SSH 场景 TUI 前端为首选。异步架构与 GTK 主循环不同范式，适合做**旁路前端**而非替换 GTK |
| urwid | s-tui 引擎，UNIX-only | 无需引入 |
| PyQt6+pyqtgraph | Argus 项目展示"驱动层共用 + TUI/GUI 双前端"三层架构（drivers→bridges→frontends） | ★★ 架构分层思想与我们 collector/controller/ui_* 天然对应，验证现结构合理 |
| GTK3 Cairo | 当前栈 | 空窗 5MB、40-80MB 常态、Cinnamon 原生主题——**实测数据继续支持维持**（GTK4 硬件加速在 UHD620 上内存 2-3 倍） |
