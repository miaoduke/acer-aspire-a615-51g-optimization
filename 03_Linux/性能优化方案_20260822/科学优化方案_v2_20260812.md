## 二、调研结果（科学依据汇总）

### 2.1 降压（undervolt）—— 全局最大单项收益

**外部依据**：
- 8 代酷睿（Kaby Lake R）**未锁降压**，10 代起才锁（erpalma/throttled README，2018-持续更新，Arch 仍打包 0.12-1，2026-06）
- 同类机型稳定参考值（均为 i5-8250U 实测）：
  - ThinkPad T480s：CPU -125 / GPU -80 / Cache -100 / SA -80（dev.to）
  - erpalma 作者 T480s：-105 / -85 / -105 / -85（官方 README）
  - Dell Latitude 7490：**-100 / -50 / -100 / -30 / -15，PL 32W，稳定 3.14GHz**（专门网 2026-02）
- 新内核（6.12+/7.0）兼容性：MSR 0x150 写警告无害，Secure Boot 关闭时直接可用（intel-undervolt issue #74，2025-06）

**本机实测依据**（降压优化报告_20260812.md）：
- **-100mV：1501.6万/s，+25.6%，2.9GHz**（15W 下同功率更高频）
- **25W + -100mV + 开盖：1638.2万/s**（全场最高）
- -100mV 满负载 180 秒零错误，无 MCE
- 0mV 下 25W 会热振荡到 96-99°C，-100mV 后仅 70-72°C

**风险评估**：低（已验证过本机体质）；方法：从 -50mV 起 25mV 步进，`stress-ng` 5 分钟验证。

### 2.2 PL1 功耗墙（15W → 25W）

**外部依据**：
- 中文社区共识（ZOL 2017 实机、专门网大量实测帖）：**8250U 的 25-30W 是性能/发热最佳平衡点**，15W 属"极度阉割"；解锁后可达 7700HQ 水平
- 散热好的机器（双风扇/双铜管，70-75°C@25W）建议放宽到 30W，但**本机单热管+单风扇不适用**

**本机实测依据**：
- constraint_0_max 虽报告 15W，写入 25W **真实生效**（冷启动实测 22-24W 功耗，吞吐 +20%）
- ⚠️ 但下午积热后 25W 长载会触发热振荡（97↔67°C 循环，吞吐跌回 1200 万级）
- **散热是最大瓶颈**：满载 86°C（Linux）/ 76°C（Windows），离 100°C 临界仅 14°C

**风险评估**：中。需配合降压 + 低温时段使用 + 高温自动降档。

### 2.3 mitigations=off（关闭 CPU 安全缓解）

**外部依据**（Phoronix 系列评测）：
- 2018 及以前架构（含 KBL-R/WHL）关闭缓解**收益明显**；新架构（Tiger Lake+）反而无效/负收益——本机正属于收益档
- i9-10900K：全局约 +4-6%，上下文切换/IO 密集负载最高 +12%
- 纯整数循环类负载收益小；浏览器、编译、系统调用密集场景收益大

**风险评估**：安全风险（Spectre/Meltdown 暴露）。家用单机可接受程度高；本机证据：Phoronix 确认 KBL-R 世代收益显著。

### 2.4 thermald / DPTF / 风扇

- 本机无 DPTF 平台设备，thermald 无配置文件 → 实际干预能力有限；保留可防"极端高温失控"，可建议**保留但无需配置**
- 风扇：hwmon 无 PWM，nbfc 对 Aspire 5 系列（A515-51G 等同代）确认不可控（多个 GitHub issue），BIOS 固件自管 → **放弃软件控风扇，散热靠清灰/硅脂**

### 2.5 工具选型

| 工具 | 能力 | 结论 |
|------|------|------|
| intel-undervolt（kitsunyan / liskin deb） | 降压 + PL + 温度目标 | ✅ 首选（静态配置 + systemd 服务即可） |
| throttled（erpalma） | 降压 + PL + 节流监控 + 暂停恢复自动重挂 | ✅ 备选，功能更全，Python 依赖 |
| TLP | WiFi/USB/磁盘/CPU 深度管理 | 可选（需停 PPD） |
| power-profiles-daemon | 三档切换（已用） | 保持 |
| nbfc-linux | 风扇 | ❌ 本机不可用 |

## 三、科学优化方案（三档，请决策）

### 方案 A —— 保守恢复（推荐，风险：低）

> 只恢复"已验证过、丢掉的"成果，不引入新风险。

1. 安装 intel-undervolt（liskin deb），按历史报告写入 **-100mV**（CPU/GPU/Cache），启用 `intel-undervolt.service`
2. 启用 `cpu-power-limit.service` 恢复 **PL1=25W**（沿用原报告内容）
3. 保持 governor=powersave / EPP 由 PPD 管理（AC=performance, DC=balanced）
4. 验证：`intel-undervolt read` 确认 -99~-100mV；跑一遍 bench

预期：AC 满载 2.9GHz 级，1200-1500 万/s；温度接近降压前水平（略降）。
旁注：现有 `优化脚本/01_02` 已含全部命令，缺的只是执行权限。

### 方案 B —— 均衡增强（推荐，风险：中）

在 A 基础上：
1. GRUB 追加 **`mitigations=off`**（保留 C-State，不影响离电续航）
2. 安装 throttled（可选替代 intel-undervolt，自带节流原因监控 `--monitor`）
3. 新增高温自动降档脚本：温度 >85°C 时 25W→15W，<70°C 恢复（基于 `温度监控.sh` 与降压报告"热振荡"教训）
4. 测试时关闭后台（ref 实测分析摘要：后台占 59% CPU）

预期：再 +5-10%（取决于工作负载）；满载安全性改善。

### 方案 C —— 极限压榨（风险：高，谨慎）

B 基础上：
1. 降压推进到 **-120mV**（实测体质探测，稳定则保留，不稳回退 -100）
2. GRUB 性能档（max_cstate 限制）— 仅插电/桌面使用，离电切回省电档
3. 清灰换硅脂（硬件操作，预计再降 10-15°C）+ 开机壳使用取得 1638 万/s 级成绩

风险：安全缓解关闭 + 极限发热 + 国标体质差异。仅建议在散热解决后尝试。

### 6.1 三档 15W 精确数据（RAPL 功耗=sysfs energy_uj 差值, ×4 修正）

| 档位 | 吞吐(万/s) | Bzy 频率(MHz) | 温度(°C) | 封装功耗(W) | 能效(万/s/W) |
|------|-----------|--------------|----------|------------|-------------|
| balanced（复测） | 1272.7 | 2564 | 85.0 | ~22 | ~58 |
| performance（复测） | 1254.2 | 2692 | 84.7 | ~23 | ~54 |
| power-saver（复测） | 372.2 | 888 | 61.2 | ~9 | ~40 |
| 25W balanced | **1343.5** | 2615 | 84.9 | ~22(限) | ~60 |
| 15W 热积累复测 | 973.6 | 2523 | **88.5** | — | 热节流 |

**结论(本轮实测)**
1. **性能 vs 平衡差异 ~1.5%（噪声内）**——与报告 13.2 节"performance 快 11%"矛盾, 原因是本轮起点温度相近(60°C), 历史观测"perf 更快"部分来自热积累效应(perf 档起点更高→更像"降频更快")。真实结论: **满载性能受 15W 功耗墙一视同仁地限制**。
2. **power-saver 能效反而最低**(40 vs 58 万/s/W): 锁频 0.89GHz 导致单位功耗产出变差——省电档仅适合续航场景, 不节能反而浪费性能(物理上 P∝f³)。
3. **PL1 写入 25W 有效**(回读 25000000, 功耗墙抬升), 但**热墙将收益压至 +5.6%**(冷态可能更高)。恢复 15W 时内核量化到 14.25W。
4. **25W 与 15W 满载 20s 温度相同(~85°C)**: 说明 85°C 已是该散热的平衡点, 功耗增量被温度墙吸收。

### 6.2 崩溃事件复盘（重要教训, 已查明）

- 过程: 完成 25W 测试后立即 15W 复测(88.5°C 起点 20s 满载), 跑完最后 1 秒**硬冻结**(断电式, 无内核日志)。
- 判定: journalctl 无 panic/MCE/thermal 记录, 前后 sudo 记录完整(唯一缺失的是从未执行的 `intel-undervolt apply`)→ **ACPI 热保护断电, 与降压无关**。
- 证据链: 起点 88.5°C(此前 25W 测试已将热库灌满)+本机 crit=100°C → 20s 满载冲过 95°C, EC 直接断电。
- **教训: ①严禁热态起点连续满载 ②测试间隔必须 ≥60s 冷却 ③温度 >80°C 时禁止跑满载。**

### 6.3 推荐方案调整（v2）

基于新数据, 三个副作用的明确排序:

| 优先级 | 措施 | 依据 | 风险 |
|--------|------|------|------|
| 1 | **清灰换硅脂**（硬件） | 85°C 满载=瓶颈铁证; 收益同时=性能上限+崩溃余量 | 无(停机即可) |
| 2 | PL1=25W + 温度保护脚本 | 实测有效+5.6~20%; 但需 >80°C 保护 | 低(服务级) |
| 3 | 降压 -50mV 保守档 | 历史 -100mV 曾有数据; 本次未验证(风险已演示) | 中(需逐步) |
| 4 | mitigations=off | 需重启验证, 收益 ≤12% | 中(引导风险) → **【已实测】详见 7.3，收益 ~4%，不推荐永久化** |

## 八、2026-08-13 上午 PL1/PL2 实测 —— 崩溃真凶确认 + 安全最优解（追加）

### 8.1 重大发现：44W 短时突刺（PL2）才是过热元凶

**背景**：上午测试期间发现 `0xa0 MSR bit38=1`（Turbo 被固件关闭，全核锁 1600MHz→吞吐骤降 775万/s）。
手动开启 Turbo 后（bit38=0）意外重现 98-99°C 峰值——**即使 PL1=15W**。

**1s 采样曲线（stress-ng 8线程 20s）暴露真相**：

| 场景 | t=2-5s | 稳态(t=10-20s) | 结论 |
|------|--------|---------------|------|
| PL1=15W + PL2=44W(默认) | **98-99°C 尖峰** | 85-88°C | ⚠️ **PL2 突刺导致尖峰** |
| PL1=15W + PL2=15W | 82-84°C 平缓 | **88°C 封顶** | ✅ 安全 |
| PL1=25W + PL2=15W | 84-86°C 平缓 | 90°C | ✅ 安全但无增益 |

**崩溃复盘修正**：6.2 节"15W 复测崩溃"的真正原因是 **PL2=44W 满载启动瞬间 + 积热起点**——
昨晚 turbostat 5s 采样间隔平滑掉了这个 1-2s 尖峰, 1s 采样才捕获。**PL2=44W 是元凶, 非 15W 本身**。

### 8.2 吞吐对比（Turbo ON, PL2=15W）

| 配置 | 吞吐(万/s) | 温度(°C) | 备注 |
|------|-----------|----------|------|
| PL1=15W+PL2=15W | **1318.3** | 60→88 | ✅ 最优, 封顶 88°C |
| PL1=25W+PL2=15W | 1319.6 | 67→90 | 无增益(散热瓶顶) |

**结论**：PL1=25W 在 Turbo ON 下**无意义**——提升的功耗全部转热（90°C 已达散热顶）。
**最佳安全配置 = PL1=15W + PL2=15W**（Turbo 保留, 性能与 25W 相当, 温度封顶 88°C, 余量 12°C）。

## 九、方法论与原理实操文档（可移植回测手册）— 2026-08-13 追加

> 目的：让任何环境（不同内核/机型/系统）下都能**复现测量 → 定位瓶颈 → 调整 → 回测**。
> 本文所有原理均给出本机实测证据与内核/硬件文档出处。

### 9.1 核心机制原理（本机实测验证 + 出处）

#### 9.1.1 RAPL 功耗墙机制（PL1/PL2/时间窗）

```
/sys/class/powercap/intel-rapl:0/
├── constraint_0 = long_term  (PL1)  power_limit_uw + time_window_us
├── constraint_1 = short_term (PL2)  power_limit_uw + time_window_us
├── energy_uj                  (只读, root) 累计能量计数器
├── intel-rapl:0:0..2          (core/uncore/dram 子域)
└── max_energy_range_uj
```

**本机实测值**：PL1=15W / time_window=**28s**；PL2=44W / time_window=**2.4ms**。

**原理（功耗=能量/时间的滑动窗口积分）**：
- RAPL 不是"瞬时硬限"，而是窗口能量预算。写入 PL1=15W 只约束 **28s 平均≤15W**，
  窗口内允许透支 —— 实测本机 15W 档满载期间封装功耗持续 **~22W**（1272万/s 一档即如此）即为透支证明。
- **PL2=44W + 2.4ms 窗口 = 满载启动瞬间（<几个 ms）即可冲到 44W** → 1-2 秒内 98-99°C 尖峰。
  这就是 6.2 节崩溃的真正机制（见 8.1）。
- **修复**：PL2 也写 15W 后尖峰消失（88°C 封顶），两者窗口单位不同但都被能量预算约束。

**出处**：Linux 内核文档 `Documentation/power/powercap/` 与 `Documentation/admin-guide/pm/intel_pstate.rst`；
Intel SDM Vol.3B Ch.15（RAPL）；turbostat(8) 手册（RAPL 采样列）。

#### 9.1.2 Turbo 机制（MSR 0x1A0 / 0x1AD）

| MSR | 含义 | 本机实测 |
|-----|------|---------|
| 0x1A0 bit38 | Turbo Mode Disable（1=关） | 开机默认 **1**（固件关闭！全核锁 1600MHz） |
| 0x1AD | turbo ratio limit（每核倍频） | 0x22222222 = 34x = 全核 3400MHz |

**原理**：Turbo 关闭时机上表现 ≠ 功耗受控，而是**频率硬锁基准**（1600MHz→吞吐腰斩 775万/s）；
打开后 HWP 自主选频（观察 2.3-2.8GHz）。关闭 Turbo 的固件默认值疑似 EC 防过热措施（开盖长测时此位=1）。

**注意**：`wrmsr -a 0x1a0` 打开 Turbo 后，25W+满载依然瞬间 99°C —— **Turbo 本身不是危险源，PL2 尖峰才是**（8.1 已验证）。

**出处**：Intel SDM Vol.3B §18.6.1（IA32_MISC_ENABLE bit38）、§15.9（Turbo）；
`/sys/devices/system/cpu/intel_pstate/no_turbo`（0=开）、`turbo_pct`（本机 59%）。

#### 9.1.3 HWP / Governor / EPP 层级

```
intel_pstate 驱动 (active 模式)
 ├── scaling_governor: powersave / performance
 ├── energy_performance_preference: performance > balance_performance > default > power
 └── scaling_cur_freq / scaling_max_freq  (3400MHz 上限实测)
```

**实测**：满载吞吐高度相同（balanced 1272.7 vs performance 1254.2 万/s）→ 15W 功耗墙下 EPP 差异被抹平。
**出处**：内核文档 `intel_pstate.rst`；本机 8.1 节数据。

#### 9.1.4 温度传感器与热保护链（崩溃机制关键）

```
coretemp（Package 温度, high=100°C crit=100°C）  ← x86_pkg_temp thermal_zone2
         ↓ 持续 >90°C
ACPI EC 固件板载保护（acpitz thermal_zone0/1, BIOS trip 119°C）
         ↓ 越过阈值
无内核日志的硬断电（ACPI 热保护）  ← 6.2 节崩溃实测现象
```

**信息来源**：coretemp 驱动 `Documentation/hwmon/coretemp.rst`（Tj_max/crit）；
本机 sensors 实测 `Package id 0: high=+100.0°C crit=+100.0°C`；
acpitz trip_point_0_temp=119000（BIOS 保护点，比内核高 19°C —— EC 断电不由内核控制、不可日志记录）。

#### 9.1.5 采样间隔陷阱（本报告最大历史教训）

| 采样间隔 | 捕获 98°C 尖峰？ | 后果 |
|---------|----------------|------|
| turbostat 5s | **否**（平滑掉） | 8.1 节前全部误判"85°C 安全" |
| sensors 1s | ✅ | 定位 PL2 元凶 |

**经验法则**：热负载测试采样间隔必须 ≤1s；本机 20s 满载 60→89°C≈1.5°C/s，突发段更快。

### 9.2 标准化测量协议（回测模板）

```
[准备] 温度 <65°C（sensors Package）；PL1/PL2 明确回读；turbo 状态记录；无重负载后台
[变量控制 - 2026-08-15 新增] 环境温度 + GPU 状态为必记变量:
   环境温度: sensors acpitz 值(本机 27-30°C), 室温每升 1°C ≈ CPU 升 ~1°C(满载 ~0.95°C),
            且不能线性修正(节流非线性, 温度低 Turbo 更激进)。前后差 >2°C 必须注明。
   GPU 状态: nvidia-smi 记录 MX150 util/temp。本机 MX150 与 CPU 共享单热管,
            独显活跃时挤占 CPU 散热能力(证据: GitHub thinkpad-firmware-patches #56,
            LTT 论坛, Acer 社区)。前后对比必须 GPU 同态, 否则数据不可比。
[测量] 1s 采样温度+平均频率（脚本见 ./bench_compare.sh 内嵌）
       20s 满载（stress-ng --cpu 8 或 ./bench 自带 8 线程 LCG）
       记录: 起点温度 / 峰值温度 / 稳态温度 / 20s 平均吞吐
[对比] 同起点温度、同配置、两次以上取均；间隔 ≥30s 冷却
[标签] 写 CSV: 日期/项目名/PL1/PL2/turbo状态/EPP/起点温度/轮次/环境温度/GPU状态
```

**可复现脚本**（本机实测全部出自它们）：
- `测量脚本/bench_compare.sh <标签>` — 两轮 15W 对比基准 + 温度保护（≥75°C 拒测、≥92°C 中止）+ 自动记录环境温度/GPU 状态（2026-08-15 更新）
- `/tmp/opencode/pl1_sample.sh` — 1s 温度/频率/PL 采样（单轮，最精确的可视化）
- `01_提升PL1功耗墙.sh`（历史）— PL1 读改验证

## 十、历史实测经验手册（跨版本对照参考）— 2026-08-13 追加

> 汇总 6.14 内核时代（实测分析摘要 / 实测数据.csv / 系统状态.csv）与 7.0 内核时代（本文档 6-8 节）
> 的**全部经验**，含方法、结论与坑。标注【6.14】= 旧内核验、【7.0】= 新内核验。

### 10.1 电源档位三档经验（【6.14】实测，2026-08-12 完整测试法）

**标准测试法**（后来 7.0 夜测沿用）：三档交错测、每档完整跑（冷启动 → 满载 → 记录起止温度/吞吐）。

| 档位 | EPP | 起温 | 止温 | 吞吐(万/s) | 相对性能 | 结论 |
|------|-----|------|------|-----------|---------|------|
| Balanced | balance_performance | 66°C | 78°C | **1384.6** | 100% | ★ 日常首选 |
| Performance | performance | 72°C | 79°C | 1352.3 | 97.7% | 热积累拖累 |
| Power-Saver | power | 53°C | 56°C | 404.6 | 29.2% | 仅极限续航 |

**经验（【6.14】+【7.0】双重确认）**：
1. **Balanced ≥ Performance**：performance 档热起步（72°C）反被节流——温度管理比档位重要
2. power-saver 锁 800-900MHz、温度几乎不升（+3°C）、能效反而最低（【7.0】验证 40 vs 58 万/s/W）
3. **热积累效应**：连续测试 1315→1213→882→737万/s（每轮 -7~-15%），必须间隔冷却
4. **温度阈值经验**（【6.14】曲线）：<60°C 全 Turbo / 60-70°C 正常 / 70-80°C 开始节流 / >80°C 严重节流 -25~-35%

### 10.2 后台负载污染教训（两代内核均踩过）

- OpenCode 桌面进程常驻 59% CPU（【6.14】）、ai.opencode.desktop GPU/render 进程 ~91%（【7.0】10:54-10:59 轮次）
- 后果：吞吐测出 780万/s 假数据（实际 1318）；mo 数据无法使用
- **对策（已验证）**：测试前 `renice -n 19` 后台进程 或 测试窗口跑 `taskset`；基准脚本内建 nice 降权
- **判断法**：若满载轮温度上升 <15°C 或吞吐 <1000万/s → 怀疑负载污染，重测

### 10.3 PL1/PL2 写入经验

| 操作 | 结果 | 教训 |
|------|------|------|
| PL1 写 25W（【7.0】夜测） | 回读 25000000 生效，冷态 +20% 吞吐 | constraint_0_max 虽报 15W，内核接受超限写 |
| 恢复 15W | 内核量化到 **14.25W**（回读非整） | 回读值 ≠ 写入值，别惊讶 |
| PL2 写 15W（【7.0】今晨） | **消除 98°C 尖峰**（88°C 封顶） | 见 8.1 崩溃真凶 |

## 十二、EPP 三档复测（重启后干净环境 + Turbo ON/OFF 对照）— 2026-08-13 11:3x 追加

## 十九、⚠️ 事故记录：-120mV 超压事故（2026-08-13）—— 最重要教训

### 19.1 事故经过
- 执行 uv_sweep.sh 测 -120mV 档时，脚本生成的 conf 为 `undervolt 0 "CPU" 120`（**丢失负号 → +120mV 超压**）
- 系统满载时卡死；强制重启后多次无法进入系统（开机时 intel-undervolt.service 自动应用 +120mV → 崩溃循环）
- 修复：手动恢复 conf 为 -100mV + apply ✅ 系统稳定

### 19.2 根因（三重失误）
1. **脚本 bug**：uv_sweep.sh 参数拼接 `undervolt 0 "CPU" $MV` 时 MV=120 未加负号 → 生成 +120mV
2. **无配置校验**：apply 前未验证 conf 数值符号/范围
3. **服务自动应用放大**：intel-undervolt.service 开机自动应用 conf → 错误配置导致开机循环崩溃

### 19.3 永久防护（立即生效的制度）
| 防护 | 内容 |
|------|------|
| ① conf 负值校验 | 写入前强制 `grep -E 'undervolt [0-9]+ "[^"]+" -[0-9]+'`，无负号即拒绝 |
| ② 正电压全拒绝 | conf 中任何无 `-` 的数字 → 禁止写入 |
| ③ 开机应用与测试解耦 | 测试档位写入 conf 前必须备份+校验；生产 conf 保持已验证值 |
| ④ 脚本参数带负号 | uv_sweep.sh 使用 `-"$MV"` 而非裸变量 |
| ⑤ apply 后必回读 | `intel-undervolt read` 确认符号与数值符合预期 |

### 19.4 科学测试安全红线（升级版）
1. **电压只能为负**：任何正值 = 硬件超压 = 立即拒绝并报告
2. **conf 写入三步校验**：写入 → cat 核对（符号+数值）→ apply
3. **apply 后必读回**：确认与预期一致
4. **测试脚本在本机自己的输出文件里比对**：生成值与目标值一致才允许 apply
5. **每档测试后恢复 conf 为已验证安全值**（-100mV），不留上次档位
6. **serious_error 即停**：MCE 计数器 >0 或系统性能异常即终止并向用户报告，绝不自动继续加压
