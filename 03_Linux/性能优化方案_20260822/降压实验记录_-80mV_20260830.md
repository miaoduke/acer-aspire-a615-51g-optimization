## 四、两项归因修正（本次最有价值的发现）

### 4.1 「DC 供电限制性能」不成立

| 配置 | 吞吐 | 与 AC 差 |
|---|---|---|
| AC (ac-perf, 25W, Turbo 开) | 1729.5 万/s | 基准 |
| **DC (bat-perf, 15W, Turbo 开)** | **1700.9 万/s** | **-1.7%** |
| DC (bat-save, 10W, Turbo **关**) | 623.5 万/s | -64% |

历史把"DC 慢"归因于电池供电能力，**实测证明主因是场景配置**：

- `~/.config/system-console/default_scene` 中 `LAST_DC=bat-save`
- 该场景将 PL1 压至 10W
- **且 `turbo-guard` 会主动关闭 Turbo**（2026-08-20 加的场景感知设计：
  检测到 bat-save 生效时不修复 no_turbo，反而主动置 1 以尊重省电决策）

**这不是故障，是设计。** 但导致"DC 性能差"的观感被误归因。

> 连带发现：`场景管理.sh` 的 bat-perf 注释称"受固件限制, 实际 PL1≈8W"——
> 实测 DC 下可写入并跑满 **15W**，该注释低估，待更新。

### 4.2 降压 MSR 不受 EC 重置影响

历史实证"拔电瞬间 EC 会重置 MSR"（11:14:56 实测）——
**该行为仅适用于 Turbo（MSR 0x1A0），不波及降压（MSR 0x150）**。

实测拔电瞬间 / +10s / +30s / +45s，降压值恒为 -80.08mV。

→ 这解释了架构差异的合理性：`turbo-enable` 需要 30s 轮询守护，
而 `undervolt` 用 oneshot 服务即可。

## 五、安全网：uv-safeguard

持久化后 `undervolt.service` 写死 -80mV，若因降压死机，重启会再次应用 -80
→ 可能陷入「死机→重启→又死机」循环。故新增：

**`/usr/local/bin/uv_safeguard.sh` + `/etc/systemd/system/uv-safeguard.service`**

- 开机检测上次启动的 journal 是否以 `systemd-shutdown` / `Journal stopped` 正常结束
- 正常 → 不动作
- 异常（硬死机戛然而止）→ **自动回退 -50mV** + 写 `/var/log/uv_safeguard.triggered` + 桌面通知
- 服务单元 `After=undervolt.service`，确保在其之后运行

**已验证**：手动执行正确判定 boot -1 为正常关机，未误触发，降压保持 -80.08mV。

> 开发中修复了一个 bug：初版用 `CUR_BOOT=0` 判断"首次运行"，
> 但 0 是合法值（当前启动恒为 0），导致守护永远跳过。已改为检查 boot 记录条数 ≥2。

**一键回退方法**（人工）：
```bash
sudo sed -i 's/--core -[0-9]*/--core -50/; s/--cache -[0-9]*/--cache -50/; s/--gpu -[0-9]*/--gpu -50/' \
  /etc/systemd/system/undervolt.service /etc/systemd/system/undervolt-resume.service
sudo systemctl daemon-reload && sudo systemctl restart undervolt
```

## 五·补 每日自检：uv-daily-check

单次测试的局限正是 -105mV 的教训：「验证通过后**数天**才死机」。
故补充一层**长期、轻量、静默**的日常巡检。

**组成**：`测量脚本/uv_daily_check.sh` + `uv-daily-check.service` + `uv-daily-check.timer`

**触发**：每日 10:00，且开机 3 分钟后补跑一次（`Persistent=true`，漏检不丢）

**检查项（7 项）**：
1. MCE 累计增量（与上次自检对比）
2. 降压值是否等于期望（允许 ±3mV 量化误差）
3. 上次启动是否异常关机
4. 关键服务 active（undervolt / turbo-enable / cpu-power-limit / acdc-profile）
5. `uv_safeguard.triggered` 是否存在
6. 电池温度可读性（监控 acer-wmi-battery，其曾因内核升级失效）
7. 内核版本变化（模块兼容性预警）

**行为**：正常 → 仅写日志，**静默**；异常 → 写 `/var/log/uv_daily_check.alert` + 桌面通知（critical）。
日志 `/var/log/uv_daily_check.log`，超 2000 行自动折半轮转。

**验证记录**（2026-08-30）：
| 场景 | 期望 | 实测 |
|---|---|---|
| 正常（-80.08mV） | 退出 0，无告警 | ✅ 通过 |
| 人为改到 -60mV | 退出 1，检出偏差 | ✅ 检出 20.43mV 并给出回退命令 |
| 恢复 -80mV 后 | 告警文件自动清除 | ✅ 通过 |

**常用命令**：
```bash
systemctl status uv-daily-check.timer      # 查看下次触发
cat /var/log/uv_daily_check.log            # 历史记录
cat /var/log/uv_daily_check.alert          # 当前告警（无异常时不存在）
sudo systemctl start uv-daily-check.service # 手动立即自检
```

## 八、遗留与下一步

1. **观察期 3-5 天**（至 2026-09-03 前后）。
   -105mV 当年是"验证通过"后**数天才死机**，故单次测试不足以定论。
   留意 `dmesg | grep -ci mce` 与是否出现 `/var/log/uv_safeguard.triggered`。

2. **-100mV 探索**（待观察期通过）。
   建议**止步 -100mV** —— -105mV 有死机 #6 史，且死机发生在电压最低的冷却期。
   必须用 `uv_sweep_v2.sh`，禁止手改服务值。

3. **未覆盖场景**：
   - 长时间（>20s）持续满载：本项目 bench 固定 20s，未做长时稳定性
   - 低温/高温环境下的 -80mV：本轮环境恒为 27.8°C
   - 挂起/休眠唤醒后的 -80mV：`undervolt-resume` 已配置但未实测验证

4. **数据污染标记**：AC 满载测试期间有 2 个后台进程 >15%（审计工具自身，
   已 renice +15）。严格按科学纪律，该批数据带轻度污染标记。
   DC 测试期间后台已降至 1 个，数据更干净。
