## 二、三个根因（第二、三个是本次才发现的）

### 根因 1：模块从未注册 DKMS
- `dkms.conf` 存在且 `AUTOINSTALL="yes"`，但 `/var/lib/dkms/` 下**只有 nvidia**。
- 一直靠手动 `make install`，装到 `/usr/lib/modules/<内核>/extra/`，vermagic 锁定单个内核。
- 内核未锁定（`apt-mark showhold` 为空）→ 升级必失效。

### 根因 2（隐蔽且致命）：Makefile 忽略 DKMS 传入的 KDIR
```makefile
# 修复前
all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules   # 无视 KDIR
```
`dkms.conf` 传的是 `MAKE[0]="make KDIR=${kernel_source_dir}"`，但 Makefile 根本不读它。

**后果链**：apt 升级内核 → DKMS 自动构建 → 此刻**尚未重启**，`uname -r` 仍是旧内核 →
按旧内核编译，却安装到新内核目录 → **vermagic 不匹配 → 加载失败**。

> 即：**若只注册 DKMS 而不修 Makefile，故障会第四次发生**，且更难排查（DKMS 显示 installed 却加载不了）。

**修复**：
```makefile
KDIR ?= /lib/modules/$(shell uname -r)/build
all:
	make -C $(KDIR) M=$(PWD) modules
```
`?=` 保证：传入时采用传入值（DKMS 场景正确），未传时保持原默认行为（手动编译场景不变）。

### 根因 3：kernel_guard.sh 的 KDIR 路径多写一截
```bash
# 修复前
make KDIR="/usr/src/linux-headers-$KERN-generic"
# $KERN 已含 -generic → 实为 ...-generic-generic（不存在）
```
此前**因根因 2 被掩盖**（KDIR 被忽略，路径错也不错）。修好根因 2 后 KDIR 开始生效，
此处会立刻暴露为 repair 失败 → 属"修复 A 引发 B"的回归，已同步修正为
`/usr/src/linux-headers-$KERN`。

> **方法论**：修一个 bug 前，先检查它是否在掩盖另一个 bug。这两个 bug 互相遮蔽了两个月。

## 四、为什么核心优化栈毫发无损

30 下复核：PL 25W/25W ✅、no_turbo=0 ✅、C-state=4 ✅、
6 个服务（cpu-power-limit / turbo-enable / undervolt / acdc-profile / thermal-guard / rasdaemon）
全 active/enabled ✅。

**唯一受损的是内核模块，因为它走的是"编译进内核目录"的路子；
凡通过 systemd 服务在开机时重新应用 sysfs/MSR 的配置，都与内核版本无关，自动恢复。**

→ 结论：**能用服务表达的调优，不要用内核模块表达**。

## 五、遗留与后续验证

- **真正的验证在下次内核升级**：届时看 `dkms status` 是否自动出现新内核版本且模块仍可加载。
  在那之前，"自动重建生效"只是推断（尽管 KDIR 修复已消除已知障碍）。

  `/home` 位于 btrfs `@home` 子卷，不受系统盘快照保护 —— **归档副本是防丢失的冗余**。
- 本归档内 `Makefile` 为**修复版**（`/home` 下同步，原文件备份为 `Makefile.bak_20260829_1303`）。

## 六、可复用的检查清单（给其他自编译内核模块）

1. 模块是否 `dkms status` 可见？不可见 → 未注册，内核升级必失效。
2. Makefile 是否支持外部传入 `KDIR`？不支持 → 注册了也没用（按旧内核编译）。
   - 自测：`make -n KDIR=/usr/src/linux-headers-<目标内核>` 看输出是否采用该路径。
3. `dkms.conf` 是否 `AUTOINSTALL="yes"`？
4. 调用方（如守护脚本）传入的 KDIR 路径是否正确？注意 `uname -r` 已含 `-generic` 后缀，勿重复拼接。
5. 源码是否备份在**非系统子卷**的位置？
